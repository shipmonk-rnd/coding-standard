# CSharpier Architecture (belav/csharpier)

Opinionated C# formatter. A near-direct port of Prettier's Wadler-style "Doc" algorithm,
built on top of Roslyn's full-fidelity syntax tree. Repo studied at
`/p/shipmonk/+tasks/oss-coding-standard-from-scratch/repos/csharpier`.

**Relevance to us:** CSharpier is the *opposite* of what we want on the normalization axis —
it fully re-prints and normalizes almost everything (one canonical form, width-driven). But two
pieces are directly reusable for a "multiple valid forms, only reformat out-of-spec code"
formatter:
1. The **Prettier Doc IR + DocPrinter** (a clean, self-contained line-breaking engine).
2. The **tree-comparison verification** (`SyntaxNodeComparer`) — re-parse the output and prove
   the edit didn't change semantics.

---

## 1. Data model: how CSharpier consumes Roslyn's lossless tree

CSharpier parses with Roslyn and walks the resulting `SyntaxTree`. It never mutates the tree —
it *reads* the tree and *emits an entirely new document* (the Doc IR), then prints that to a
string. So it is a full re-printer, not an edit-in-place tool.

- Parse entrypoint: `CSharpFormatter.ParseText` uses `CSharpSyntaxTree.ParseText` with
  `LanguageVersion.Preview` — `Src/CSharpier.Core/CSharp/CSharpFormatter.cs:79-96,13`.
- Root must be a `CompilationUnitSyntax` — `CSharpFormatter.cs:105-111`.
- Before formatting it rejects files with compile errors (bails out returning the original
  source) — `CSharpFormatter.cs:121-146`. This is a precondition, not the semantic check in §5.
- Main pipeline: `Node.Print(rootNode, context)` (tree -> Doc) then
  `DocPrinter.Print(document, ...)` (Doc -> string) — `CSharpFormatter.cs:162-163`.

### Trivia handling (whitespace + comments)

Roslyn attaches all whitespace/newlines/comments/directives as **leading/trailing trivia** on
tokens. CSharpier *does not* copy trivia through verbatim; it re-interprets it:

- Every token is printed via `Token.PrintSyntaxToken`, which explicitly prints leading trivia,
  then the token text, then trailing trivia — `Src/CSharpier.Core/CSharp/SyntaxPrinter/Token.cs:39-164`.
- **Whitespace/newlines in trivia are discarded** and regenerated by the printer. In
  `PrivatePrintLeadingTrivia` (`Token.cs:237-391`) `WhitespaceTrivia` is never emitted, and
  `EndOfLineTrivia` is only turned into at most a controlled `HardLine` — indentation is owned by
  the DocPrinter, not the source.
- **Comments are preserved verbatim as text**, emitted as `LeadingComment`/`TrailingComment`
  Docs (`Token.cs:295, 421-425`; types in `DocTypes/LeadingComment.cs`, `TrailingComment.cs`).
  The DocPrinter re-indents multi-line comments by measuring the delta of the first line's indent
  and shifting the rest by the same amount — `DocPrinter.AppendComment`, `DocPrinter.cs:191-250`.
- **Directives / disabled text** (`#if`, `#region`, code inside inactive `#if`) are preserved as
  literal `Doc.Directive` / `Doc.Trim` + raw text, and marked so they don't count toward line
  width — `Token.cs:311-353`, and `IsDirective` skipped in fitting (`DocFitter.cs:50-52`).
- Verbatim/raw/interpolated strings are emitted using `LiteralLine` (a hard line that resets
  column to 0 without indentation) so their internal content is kept byte-exact — `Token.cs:63-129`.

Takeaway for us: CSharpier's model is "read tree, throw away original whitespace, regenerate."
A multi-form formatter would instead want to *inspect* trivia (line-break positions) and only
rewrite when out of spec — CSharpier deliberately does not, which is why its output is canonical.

## 2. The "Doc" IR and the group/fits/break algorithm

The IR is in `Src/CSharpier.Core/DocTypes/`. `Doc` is the abstract base with static factory
helpers (`Doc.cs:5-223`), plus an implicit `string -> StringDoc` conversion (`Doc.cs:12-15`).

### Doc node types (all subclass `Doc`)
| Doc | File | Meaning |
|---|---|---|
| `StringDoc` | `StringDoc.cs` | literal text (`IsDirective` flag excludes it from width) |
| `Concat` | `Concat.cs` | ordered list of Docs |
| `Group` | `Group.cs` | unit that prints **flat if it fits**, else **broken**; optional `GroupId`, `Break` flag |
| `ConditionalGroup : Group` | `ConditionalGroup.cs` | ordered `Options[]`; first that fits wins, else last |
| `IndentDoc` | `IndentDoc.cs` | increase indent for contents |
| `LineDoc` | `LineDoc.cs` | line with `LineType { Normal, Hard, Soft }`, `IsLiteral`, `Squash` |
| `HardLine : LineDoc` | `HardLine.cs` | always breaks; implements `IBreakParent` |
| `LiteralLine : LineDoc` | `LiteralLine.cs` | hard line that also resets column with no indent |
| `IfBreak` / `IndentIfBreak` | `IfBreak.cs` | pick `BreakContents` vs `FlatContents` based on a group's mode |
| `ForceFlat` | `ForceFlat.cs` | force contents to print flat |
| `BreakParent` | `BreakParent.cs` | marker (`IBreakParent`) that forces enclosing group to break |
| `Trim` | `Trim.cs` | trims trailing whitespace already emitted |
| `LeadingComment`/`TrailingComment` | resp. files | comment text |
| `Region` | `Region.cs` | `#region` / `#endregion` with indent tracking |
| `AlwaysFits` | `AlwaysFits.cs` | wraps content so it never counts against width |
| `NullDoc` | `NullDoc.cs` | no-op |

Semantics of the three fundamental lines (in `DocPrinter.ProcessLine`, `DocPrinter.cs:279-332`):
- **`Line` (Normal)**: a space when flat, a newline+indent when broken.
- **`SoftLine`**: nothing when flat, newline+indent when broken.
- **`HardLine`**: always a newline; also *propagates a break* to its enclosing group.

### Line-breaking algorithm

Two-phase, exactly like Prettier:

**Phase A — `PropagateBreaks.RunOn(document)`** (`DocPrinter/PropagateBreaks.cs:12-140`,
invoked at `DocPrinter.cs:37`). A single stack-based tree walk: any `IBreakParent`
(`HardLine`, `BreakParent`, `LiteralLine`) sets `Break = true` on the nearest enclosing `Group`,
and a broken child group propagates `Break` up to its parent on exit (`PropagateBreaks.cs:71-86`).
So a group containing a forced newline is pre-marked broken before printing.

**Phase B — `DocPrinter.Print`** (`DocPrinter.cs:42-58`): a work-stack of `PrintCommand
(Indent, PrintMode, Doc)` (`DocPrinter.cs:408`), mode is `Flat | Break | ForceFlat`
(`DocPrinter.cs:410-415`). Tracks `CurrentWidth` and appends to a `StringBuilder`.

Group handling is the core — `DocPrinter.ProcessGroup` (`DocPrinter.cs:334-387`):
1. If already in flat mode and not forced to remeasure, print contents flat (or broken if
   `group.Break`).
2. Otherwise build a trial command in `PrintMode.Flat` and ask **`Fits`**.
3. If `!group.Break && Fits(...)` -> print flat. Else -> print `PrintMode.Break`.
4. `ConditionalGroup`: try each option in order, take the first that `Fits`, else the last
   (most-expanded) — `DocPrinter.cs:349-376`.
5. If the group has a `GroupId`, record the chosen mode in `GroupModeMap` so later `IfBreak`s
   keyed to that id can react (`DocPrinter.cs:383-386`).

**`Fits`** — `DocPrinter/DocFitter.cs:9-155`. Given remaining width (`Width - CurrentWidth`,
`DocPrinter.cs:394`), it simulates printing the trial command *plus* the already-queued
`remainingCommands`, in flat mode, accumulating width:
- returns `false` the moment `remainingWidth < 0` (`DocFitter.cs:33-35`);
- a `Line`/`HardLine` reached in break mode -> **fits (true)**, because the content up to the
  next line break fit (`DocFitter.cs:119-141`);
- directives and `AlwaysFits` don't consume width (`DocFitter.cs:50-52,147-148`);
- comments encountered after real output force a `false` (`DocFitter.cs:63-69`).

Net effect: each `Group` independently chooses flat-vs-broken by measuring whether its flat
rendering (and the following text up to the next hard break) fits within `PrinterOptions.Width`.
This is the classic Prettier width-break. Default print width lives in `PrinterOptions` /
`CodeFormatterOptions` (`Src/CSharpier.Core/PrinterOptions.cs`).

## 3. Formatting flow: Roslyn tree -> Doc IR -> string

`CSharpFormatter.FormatAsync(SyntaxTree, ...)` — `CSharpFormatter.cs:98-223`:
1. `syntaxTree.GetRootAsync()` -> `CompilationUnitSyntax` (`:105`).
2. Skip auto-generated files (`:113-119`); bail on compile errors (`:143-146`).
3. Build a `PrintingContext` (line-ending, indent size, tabs) — `:151-161`.
4. **`Node.Print(rootNode, context)`** produces the Doc — `:162`.
5. **`DocPrinter.Print(document, printerOptions, lineEnding)`** produces the string — `:163`.
6. Re-run over each preprocessor symbol set so `#if`/`#else` branches are also formatted
   (re-parse formatted code per symbol set) — `:170-202` (`PreprocessorSymbols.GetSets`).
7. Returns `CodeFormatterResult` with the code plus flags `ReorderedModifiers`,
   `ReorderedUsingsWithDisabledText`, `MovedTrailingTrivia` — `:204-214` (these feed §5).

**`Node.Print` is source-generated.** The dispatcher is generated from
`Src/CSharpier.Generators/NodePrinterGenerator.sbntxt` into a big `switch` on
`syntaxNode.RawKind` that delegates to a per-node-type printer
(`NodePrinterGenerator.sbntxt:38-47`; depth guard `>200` throws `InTooDeepException` at `:22-25`).
The ~160 hand-written per-node printers live in
`Src/CSharpier.Core/CSharp/SyntaxPrinter/SyntaxNodePrinters/*.cs` (one file per syntax node, e.g.
`InitializerExpression.cs`, `ArgumentList.cs`). Shared helpers (separated lists, trailing comma,
modifiers, optional braces, extra new-lines) are in `SyntaxPrinter/*.cs`. A per-node printer
returns a `Doc` built from the factories in §2; e.g. `InitializerExpression.Print` wraps its
contents in `Doc.Group(...)` with `Doc.Line` separators
(`SyntaxPrinter/SyntaxNodePrinters/InitializerExpression.cs:35-72`).

So: **Roslyn `SyntaxTree` → (per-node printers) → `Doc` tree → `PropagateBreaks` → `DocPrinter`
→ string.**

## 4. Preservation of user formatting: almost none (fully normalizes)

CSharpier is opinionated: for a given input it emits one canonical form. It does **not** keep a
collection/argument list expanded just because the user wrote it expanded. There is **no "magic
trailing comma"** and essentially no line-break-preservation heuristics (a repo-wide grep for
`GetLineSpan`/`LineSpan`/newline-in-trivia checks inside the node printers found only
`BaseMethodDeclaration.cs`). Breaking is decided purely by:
- **width** (the Group/`Fits` algorithm, §2), and
- **deterministic content heuristics**, e.g. `InitializerExpression.Print`'s `alwaysBreak` when an
  object/collection initializer has `>= 3` expressions, or a nested array initializer
  (`SyntaxPrinter/SyntaxNodePrinters/InitializerExpression.cs:17-33`). This depends on *count*,
  not on how the user laid it out.

What it **does** preserve:
- **Comments** — kept verbatim (text and, for multi-line, internal alignment) — `Token.cs:283-309`,
  `DocPrinter.cs:191-250`.
- **A single blank line** between members / after `{` — collapses any run of blank lines to at most
  one. `ExtraNewLines.Print` scans leading trivia and emits exactly one `Doc.HardLine` if any
  blank line existed, else nothing — `SyntaxPrinter/ExtraNewLines.cs:15-31`; applied in member
  printers and `Node` (`NodePrinterGenerator.sbntxt:30-32`). So blank-line *presence* is
  preserved but the *count* is normalized to one.
- **Disabled/`#if` code and directives** — kept as literal text (`Token.cs:311-353`).
- **Verbatim/raw string contents** — kept exactly (`Token.cs:63-129`).
- `// csharpier-ignore` regions — printed unformatted (`SyntaxPrinter/CSharpierIgnore.cs`,
  `NodePrinterGenerator.sbntxt:27-33`).

**Contrast for our project:** we want the *inverse* policy — accept multiple valid forms and only
rewrite out-of-spec code. CSharpier shows the machinery (Doc IR + width engine) but hard-wires a
single form. To allow multiple forms you would either (a) add source-driven heuristics in the
per-node printers (inspect original trivia line breaks and choose `HardLine` vs `Line`
accordingly — the "magic trailing comma" pattern Prettier uses), or (b) not re-print conforming
nodes at all and only splice fixes for violations. CSharpier does neither.

## 5. Verification: re-parse output and compare syntax trees

After formatting, the CLI re-parses the formatted output and structurally compares it to the
original tree to prove no code changed (only whitespace/trivia). Wiring:

- `Src/CSharpier.Cli/CommandLineFormatter.cs:514-581`: unless `--skip-validation`, and only when
  the output differs from input (`:518-521`), it builds a `SyntaxNodeComparer(originalSource,
  formattedSource, reorderedModifiers, reorderedUsingsWithDisabledText, movedTrailingTrivia, ...)`
  (`:528-536`), wraps it in `CSharpFormattingValidator` (`:538`), and calls `ValidateAsync`
  (`:556`). A failure increments `FailedFormattingValidation` and reports an error (`:559-567`) —
  i.e. CSharpier refuses to trust its own output silently.

`SyntaxNodeComparer` — `Src/CSharpier.Core/CSharp/SyntaxNodeComparer.cs`:
- Ctor re-parses **both** the original and the formatted source into fresh `SyntaxTree`s
  (`:38-52`).
- `CompareSourceAsync` (`:60-86`) walks both roots via `AreEqualIgnoringWhitespace` (`:132-149`),
  an explicit dual-stack DFS (`originalStack`/`formattedStack`, `:129-130`) — no recursion, so
  deep trees don't overflow. Returns `""` on success, or a human-readable diff with source line
  context (`GetLine`, `:88-127`) on mismatch.
- The per-node `Compare((node,parent),(node,parent))` dispatcher and all `CompareXxxSyntax`
  methods are **source-generated** by `Src/CSharpier.Generators/SyntaxNodeComparerGenerator.cs`.
  For every Roslyn node type it emits a method comparing each property
  (`SyntaxNodeComparerGenerator.cs:134-288`):
  - `bool`/`int` properties must be equal (`:193-198`);
  - `SyntaxToken` -> `Compare(token, token, ...)` (`:199-205`);
  - child `CSharpSyntaxNode` -> pushed onto both stacks (`:213-221`);
  - `SyntaxList`/`SeparatedSyntaxList` -> `CompareLists`, and crucially the **last separator is
    omitted** so an added/removed trailing comma is allowed (`AllSeparatorsButLast`,
    `:216-239` in comparer, `:271-275` in generator);
  - it deliberately **ignores** `HasLeadingTrivia`/`HasTrailingTrivia`/`SpanStart` etc. because
    whitespace legitimately changes (`:160-173`);
  - `TypeDeclaration`/`MethodDeclaration` short-circuit via `CompareFullSpan` (byte-equal fast
    path) (`:144-154`).
- The **whitespace-insensitive** comparison is what makes this a semantic check:
  - Token text must match modulo `\r` (`SyntaxNodeComparer.cs:316-328`);
  - trivia comparison (`Compare(SyntaxTrivia...)`, `:343-373`) skips whitespace/EOL, compares
    comments line-by-line trimmed (`CompareComment`, `:386-414`), and compares disabled `#if`
    text via `DisabledTextComparer.IsCodeBasicallyEqual` (`:345-358`);
  - `Compare(SyntaxTriviaList...)` (`:416-509`) iterates only the *significant* trivia
    (`FindNextSyntaxTrivia` skips whitespace/EOL, `:418-437`), so reflow of blank lines/indent
    passes but a lost or moved comment fails.
- Known safe transformations that *do* reorder tokens are guarded by the flags threaded from
  formatting: `ReorderedModifiers`, `MovedTrailingTrivia`, `ReorderedUsingsWithDisabledText`
  (usings-with-disabled-text simply short-circuits to "equal", `:65-68`) — the comparer relaxes
  exactly those cases (`:275-293, 336-341, 547-564`).

**Takeaway for us — this is the highest-value idea.** A "prove the edit is safe" gate:
re-parse the formatter's output, structurally diff against the original tree ignoring
trivia/whitespace, and reject the change if anything but whitespace/comment-layout differs. The
implementation notes worth copying:
1. Compare on a **fresh re-parse of the emitted text**, not on an in-memory manipulated tree —
   catches bugs where the printer produced text that parses differently.
2. Ignore-whitespace comparison with **explicit allow-lists** for intended token moves (trailing
   comma add/remove, modifier reorder, using sort). Everything else must be byte/structure equal.
3. Iterative dual-stack walk (no recursion) for robustness on large/deep files.
4. Compare comments by trimmed content so re-indentation is allowed but comment loss is caught.
